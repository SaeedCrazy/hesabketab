# پژوهش ۰۱ — انتقال داده از نرم‌افزارهای حسابداری رایج (بخش الف)

> **پروژه:** حساب‌کتاب (hesabketab): پلتفرم حسابداری/ERP همه‌منظوره، به‌صورت SaaS چندمستاجری و نصب محلی
> **تاریخ پژوهش:** ۲۶ آبان ۱۴۰۵ (2026-11-17)
> **دامنه:** هلو، سپیدار (نصبی و ابری)، محک، حسابفا، پارمیس و چند محصول ابری دیگر. این سند موتور پایگاه داده، فایل پشتیبان، خروجی و ورود اکسل، API، ابزارهای تبدیل موجود و اسکیمای شناخته‌شده را بررسی می‌کند و بر همین اساس راهبرد انتقال داده در حساب‌کتاب را پیشنهاد می‌دهد.
> **سطح اطمینان:** ادعاهای مهم برچسب «اطمینان: بالا / متوسط / پایین» دارند.

> ⚠️ **محدودیت روش پژوهش:** وب‌سایت‌های ایرانی (holoo.co.ir، sepidarsystem.com، hesabfa.com، mahaksoft.com، parmisit.com و نمایندگی‌ها) و همچنین web.archive.org از محیط پژوهش در دسترس نبودند (پاسخ 503 یا قطع اتصال). اطلاعات این سایت‌ها از **خلاصه‌های موتور جستجو** آمده و برای همین اطمینانشان یک پله پایین‌تر از خواندن مستقیم است. شواهد فنی اسکیما بیشتر از **کد متن‌باز ابزارهای مهاجرت واقعی در GitHub** آمده است، مثل ابزار Holoo2Hesabix، طرح «ورود لایو سپیدار» حسابیکس و ADRهای SabalanERP. در این کدها با پایگاه دادهٔ واقعی مشتری کار شده است. مستندات Microsoft مستقیم خوانده شد. پیش از پیاده‌سازی، هر ادعای «متوسط» یا «پایین» باید روی یک نصب واقعی (با رضایت مالک داده) دوباره بررسی شود.

> 🔎 **راستی‌آزمایی مستقل (۲۶ آبان ۱۴۰۵):** ۱۵ ادعای کلیدی این سند جداگانه بررسی شد. نتیجه: ۵ تأیید، ۸ اصلاح و ۲ نامطمئن. اصلاح‌ها در متن با برچسب «[اصلاح‌شده در راستی‌آزمایی]» آمده‌اند و جزئیات در بخش آخر («گزارش راستی‌آزمایی») است. مهم‌ترین اصلاح‌ها: سقف Express در SQL Server 2025 به **۵۰ GB** رسیده است؛ `ApplicationIntent=ReadOnly` جلوی نوشتن را **نمی‌گیرد**؛ TncHoloo برخلاف متن اولیه **گزارش ماندهٔ سرفصل و ثبت سند دریافت و حواله** دارد؛ و مخزن حسابیکس طبق README خود **GPL-3.0** است.

## ۱. خلاصهٔ اجرایی

1. **همهٔ نرم‌افزارهای نصبی این فهرست روی Microsoft SQL Server کار می‌کنند** (هلو، سپیدار، محک، پارمیس؛ اطمینان: هلو و سپیدار بالا، پارمیس متوسط تا بالا، محک متوسط). پس یک «لایهٔ استخراج عمومی از SQL Server» به‌اضافهٔ یک «پروفایل نگاشت» برای هر فروشنده بیشترین بازده را دارد. لازم نیست برای هر محصول ابزار جدا بسازیم.
2. **هلو:** دیتابیس SQL Server با نام پیش‌فرض `Holoo1`. پیش‌فرض نصب SQL Server 2008 R2 است و collation فارسی دارد. جدول‌های کلیدی `SARFASL` (کدینگ)، `SANAD`/`SND_LIST` (اسناد)، `CUSTOMER`، `ARTICLE`، `FACTURE`/`FACTART`، `[Check]`، `ACOUND_N`، `Cash` و `MONEY` هستند. کدینگ حساب‌ها ثابت و سه‌سطحی است: کلِ سه‌رقمی، معین چهاررقمی و تفصیلی. پشتیبان یک فایل **ZIP** با گزینهٔ رمز است. ورود اکسل فقط برای کالا، طرف حساب و چک وجود دارد. API رسمی (TncHoloo، یک سرویس ویندوزی جاوا روی پورت 8080) جدا فروخته می‌شود و **فهرست کامل اسناد حسابداری را برنمی‌گرداند**. ولی طبق راهنمای وب‌سرویس، ماندهٔ هر سرفصل را در بازهٔ تاریخ (`Report/GetSarfasl`)، کاردکس سرفصل، و موجودی بانک و صندوق را می‌خواند. ثبت سند حواله و دریافت از طرف حساب را هم دارد. [اصلاح‌شده در راستی‌آزمایی] (اطمینان: متوسط؛ راهنمای نسخهٔ حدود ۲۰۱۹.)
3. **سپیدار:** دیتابیس SQL Server (مثلاً `Sepidar01`) با چند schema (`ACC`، `GNR`، `INV`، `SLS`، `RPA`، `FMK` و …). در یک نصب واقعی حدود ۳۷۹ جدول دیده شده است. ساختار حساب «گروه/کل/معین» به‌اضافهٔ **تفصیلی شناور** (`ACC.DL`) است و چند سال مالی در یک دیتابیس نگهداری می‌شود. پشتیبان یک فایل باینری SQL Server است و امکان فشرده‌سازی و رمز دارد. ولی اینکه پشتیبانِ رمزدار یک `.bak` خام قابل `RESTORE` باشد **تأیید نشد** (بخش ۳.۲). [اصلاح‌شده در راستی‌آزمایی] وب‌سرویس رسمی سپیدار (v110/v112) فقط خواندن مشتری، کالا، فاکتور و موجودی را پوشش می‌دهد. دریافت در آن **فقط ثبت (POST)** است و خواندنی نیست. **سرفصل یا سند حسابداری هم ندارد.** پس انتقال دفتر کل از SQL یا قالب‌های اکسل «ارسال و دریافت اطلاعات» انجام می‌شود.
4. **حسابفا (ابری):** دسترسی مستقیم به دیتابیس ممکن نیست. **API رسمی کامل** دارد (`https://api.hesabfa.com/v1/...` با `apiKey` و `loginToken`): اشخاص، کالا، فاکتور، دریافت/پرداخت، **سند حسابداری**، **فهرست حساب‌ها** (`setting/GetAccounts`) و **تراز آزمایشی** (`report/trialbalance`). بنابراین با کلیدی که خود مشتری می‌سازد، انتقال کامل و قابل تطبیق شدنی است (اطمینان: بالا).
5. **محک و پارمیس:** اسکیمای عمومی‌شده‌ای ندارند. ورود اکسل در محک فقط در راه‌اندازی اولیه و با بانک خالی ممکن است (کالا و اشخاص با ماندهٔ اول دوره). محک یک API همگام‌سازی ابری دارد (`mahakacc.mahaksoft.com/API/v3/Sync`) که کالا، اشخاص، سفارش و تراکنش را پوشش می‌دهد. پارمیس ورود اکسل کالا و چک و یک API اختصاصی برای فروشگاه دارد. برای این دو باید با رضایت مشتری یک **probe فقط‌خواندنی** روی دیتابیس واقعی اجرا شود.
6. **بازار خدمات «کانورت» فعال است** اما بیشتر دستی و اکسل‌محور است. ابزارهای خودکار شناخته‌شده: Holoo2Hesabix و «ورود لایو سپیدار» (هر دو از حسابیکس متن‌باز)، مبدل هلو به حسیب (دو مرحله: اطلاعات اولیه و سپس گردش عملیات)، و شرکت‌های نمایندهٔ سپیدار که هلو را با اکسل به سپیدار منتقل می‌کنند.
7. **درس‌های سخت از مهاجرت‌های واقعی:**
   - (الف) اسناد حسابداریِ ساخته‌شده از فاکتور یا چک نباید دوباره منتقل شوند (خطر **ثبت دوبل**).
   - (ب) هرگز حساب نامشخص را به «اولین بانک» یا «اولین صندوق» یا حساب معلق نسبت ندهید. سند را **مسدود (Block)** کنید.
   - (ج) پذیرش نهایی یعنی **تطبیق تراز آزمایشی با اختلاف توضیح‌داده‌نشدهٔ صفر**.
   - (د) اجرای مجدد باید idempotent باشد و برای هر رکورد ردِ مبدأ (lineage) نگه دارد.
   - (هـ) موجودی و بهای تمام‌شده ظریف‌ترین بخش‌اند: قیمت نامعلوم را صفر فرض نکنید.
8. **راهبرد پیشنهادی:** خط لولهٔ مرحله‌ای *Discover → Extract → Normalize → Map → Validate → Preview → Commit → Reconcile → (Rollback)* روی یک **قالب میانی استاندارد** (پیشنهاد: «بستهٔ تبادل حساب‌کتاب»، HIF). ورودی از سه کانال می‌آید: API (ابری‌ها)، SQL Server (عامل ویندوزی فقط‌خواندنی یا بازیابی `.bak` در sandbox ایزوله) و قالب‌های اکسل/CSV جهانی برای هر نرم‌افزار دیگر. دامنهٔ پیش‌فرض: **اطلاعات پایه + تراز افتتاحیه + اقلام باز در مرز سال یا ماه**. تاریخچهٔ قبلی به‌صورت آرشیو فقط‌خواندنی می‌آید و در صورت درخواست، تاریخچهٔ کامل با ردِ مبدأ.
9. **قید حقوقی و اخلاقی:** فقط دادهٔ خود مشتری و با مجوز صریح او. رمز پشتیبان، قفل نرم‌افزار یا رمزنگاری فروشنده را بدون رضایت و مجوز **نمی‌شکنیم**. دسترسی غیرمجاز به دادهٔ محافظت‌شده طبق ماده ۱ قانون جرایم رایانه‌ای (ماده ۷۲۹ تعزیرات) جرم است. از کد، اسکریپت یا SP فروشنده هم کپی نمی‌کنیم.

## ۳. یافته‌های تفصیلی هر محصول

### ۳.۱ هلو (Holoo؛ شرکت مهندسی نرم‌افزار هلو / گروه طرفه‌نگار)

**موتور و نصب**
- موتور: **Microsoft SQL Server**. نصب پیش‌فرض با SQL Server 2008 (R2) است و نسخه‌های 2012 تا 2019 نصب دستی می‌خواهند. راهنمای هلو توصیه می‌کند collation روی **Persian** تنظیم شود. (اطمینان: بالا. منابع: help.holoo.co.ir از طریق نتایج جستجو و آموزش‌های نصب.)
- نام دیتابیس معمولاً `Holoo1` است و نام‌هایی مثل `Holoo2` هم دیده شده‌اند. معلوم نیست `Holoo2` شرکت دوم است یا سال بعد. در چند کد مستقل GitHub (ابزار Holoo2Hesabix، اتصال وب‌سرویس، کوئری‌های گزارش) نام `Holoo1` به‌عنوان پیش‌فرض آمده است. (اطمینان: بالا برای `Holoo1`، پایین برای معنای `Holoo2`.)
- instance می‌تواند پیش‌فرض (`MSSQLSERVER`) یا نام‌دار باشد (در یک ابزار نمونه `localhost\HOLOO`). باید کشف شود و فرض نشود. (اطمینان: پایین.)
- یک ابزار شخص ثالث گزارش داده که روی دیتابیس هلو تابع `TRY_CONVERT` کار نمی‌کند. یعنی سطح سازگاری قدیمی (≤ 2008 R2، compatibility 100) است. یک fixture دیگر هدر پشتیبانی با `DatabaseVersion 661` (2008 R2) و collation `Persian_100_CI_AS` را مدل کرده است. (اطمینان: متوسط.)
- تاریخ‌ها در ستون‌های `datetime` میلادی ذخیره می‌شوند (`Sanad_Date`، `Fac_Date` و تاریخ‌های چک). (اطمینان: متوسط تا بالا، از کد خواندن اسناد Holoo2Hesabix.)
- واحد پول به گفتهٔ یک سند فنی شخص ثالث «ریال صحیح» است. باید روی هر نصب با نمونه‌گیری تأیید شود. (اطمینان: پایین تا متوسط.)
- **نسل جدید: هلو APEX** (رونمایی ۱۴۰۰). رابط کاربری بازطراحی شده، «کدهای حسابداری تغییر کرده‌اند» و اتصال افزونه‌ها از طریق APIDOC و SANDBOX است. ممکن است اسکیمای APEX با هلوی کلاسیک فرق داشته باشد، پس پروفایل باید نسخه‌محور (version-aware) باشد. (اطمینان: متوسط.)

**پشتیبان**
- منو: «اطلاعات پایه / امکانات ← تهیه و بازیابی کپی پشتیبان». فایل از نوع **ZIP** است و پیش‌فرض در پوشهٔ `Holoo.bak` داخل مسیر نصب ذخیره می‌شود. گزینهٔ **«با کلمه عبور»** هم وجود دارد. بازگردانی جایگزین دادهٔ فعلی می‌شود و چیزی اضافه نمی‌کند. (اطمینان: متوسط تا بالا؛ چند آموزش مستقل.)
- محتوای داخل ZIP (احتمالاً یک `.bak` یا فایل‌های داده‌ی SQL) در منابع عمومی تأیید نشد. **سؤال باز.** اگر مشتری رمز گذاشته باشد، رمز را خود مالک باید وارد کند.

**اسکیمای کلیدی** (از کد متن‌باز Holoo2Hesabix و مستند مهندسی معکوس DakkeManager؛ اطمینان: متوسط تا بالا. در عمل روی دیتابیس واقعی اجرا شده‌اند.)

**نکته‌های پنهان** (هر کدام در یک مهاجرت واقعی باعث خطا شده است)
1. در یک نمونه ۵۳۸ فاکتور با `SaveFromFacture = 0` به سند نوع 13/14 وصل بودند. اگر هم فاکتور و هم «سند دستی» منتقل شوند، فروش و خرید **دوبار ثبت می‌شود**. سند متصل به `FACTURE` غیرحذف‌شده یا به `[Check]` باید از انتقال دستی کنار گذاشته شود.
2. ردیف‌های `005`/`006` و GL چک (`Sanad_Type=5`) کپی نمی‌شوند. اثرشان از ماژول افتتاحیه و ماژول چک ساخته می‌شود.
3. **۱۲ بانک و ۲ صندوق:** نگاشت با «اولین بانک یا صندوق» یا تطبیق `Contains` روی نام، مانده را بی‌صدا به حساب غلط می‌برد. تطبیق فقط با نقشهٔ صریح یا شمارهٔ حساب دقیق مجاز است.
4. وام‌ها زیر `401` با بستانکاران تجاری قاطی می‌شوند و باید تفکیک شوند.
5. موجودی اول دوره: سطر ریالی از کل `106` می‌آید و مقدار از `ARTICLE.First_exist`. هر دو را به GL نبرید، چون **دوبل** می‌شود.
6. در یک نصب از ۲۹٬۰۷۱ کالا فقط یکی گروه داشت (`M_Code`)، و `ARTICLE.Sel_Price` با `ArticlePrice` در ۲۲٬۱۳۲ مورد متفاوت بود. منبع حقیقتِ «قیمت» باید با مشتری قطعی شود.

**ورود و خروج اکسل**
- **خروجی:** گزارش‌های ستونی (از جمله تراز آزمایشی و دفاتر کل، معین و تفصیلی) به Excel، Text و HTML. در نسخه‌های پیشرفته پیش‌فرض است و در بقیه با کیت کم‌هزینه اضافه می‌شود. خروجی اکسل کالا، طرف حساب و چک هم هست. (اطمینان: متوسط.)

**API**
- وب‌سرویس رسمی **TncHoloo** با آدرس `http://<server>:8080/TncHoloo/api/`. ورود با نام دیتابیس، کاربر و رمز. پوشش: مشتری (`Customer`)، گروه، واحد و کالا (`MainGroup` و …)، فاکتور و پیش‌فاکتور. ارجاع‌ها با `erpcode` (base64) انجام می‌شوند. افزونهٔ فروشگاهی «نیلا» روی همین سرویس کار می‌کند. (اطمینان: متوسط.)
- [اصلاح‌شده در راستی‌آزمایی] راهنمای رسمی وب‌سرویس (`docs/WebService-Guide.pdf` در مخزن zoghal/HolooWebService) نشان می‌دهد پوشش حسابداری **محدود ولی موجود** است:
  - سرویس یک Windows Service مبتنی بر جاوا (JRE 8) با نام `TncHolooWebService` است و روی HTTP ساده کار می‌کند.
  - `POST /Login` با بدنهٔ `{"userinfo":{"username","userpass"(Base64),"dbname":"Holoo1"}}` یک توکن Bearer می‌دهد.
  - **گزارش‌ها (GET):** `Report/GetSarfasl` (ماندهٔ هر سرفصل با `code` و `date.from`/`date.to`)، `Report/GetKardexSarfasl` (کاردکس بدهکار و بستانکار یک سرفصل)، `Report/GetAccound` (ماندهٔ بانک)، `Report/GetCash` (صندوق) و `Report/GetCustPay`.
  - **ثبت سند:** `api/Payment/Havaleh` (حوالهٔ طرف حساب) و `api/Payment/ReciveFromCus` (دریافت از طرف حساب). کدهای سرفصل در نمونه‌ها سه‌سطحی‌اند: `102`+`0001`+`0001`.
  - **فهرست کامل اسناد (`SANAD`/`SND_LIST`) را برنمی‌گرداند.** پس برای انتقال دفتر کل همچنان SQL لازم است. ولی `GetSarfasl` در تاریخ cutover برای **کنترل تطبیق تراز افتتاحیه** مفید است.
  - مبالغ به‌صورت رشتهٔ اعشاری علمی برمی‌گردند (مثل `"3.25787252E8"`). باید با `Decimal` پارس شوند و با SQL تطبیق داده شوند، نه اینکه مرجع نهایی باشند.
  - نسخهٔ راهنما قدیمی است (نمونه‌ها ۲۰۱۹). پوشش در نسخهٔ فعلی و APEX باید تأیید شود.

### ۳.۲ سپیدار (Sepidar System؛ نصبی)

**موتور و نصب**
- موتور: **SQL Server**. نام instance رایج **`SEPIDAR`** است (سرویس `MSSQL$SEPIDAR`). اتصال با Windows Auth یا `sa` برقرار می‌شود. ابزار `DatabaseSetup.exe` در مسیر نصب برای پشتیبان‌گیری و بازیابی است. (اطمینان: متوسط تا بالا.)
- نام دیتابیس به شکل `Sepidar01` است. در یک انتقال واقعی، ۳۷۹ جدول و ۱۳۶٬۲۴۲ رکورد خوانده شد. (اطمینان: بالا. طرح «ورود لایو سپیدار» حسابیکس، گزارش پذیرش ۲۳ اکتبر ۲۰۲۶.)
- **چند سال مالی در یک دیتابیس:** جدول `FMK.FiscalYear` و ستون `FiscalYearRef` در جدول‌های عملیاتی. یک پشتیبان واقعی هم‌زمان سال‌های ۱۴۰۴ و ۱۴۰۵ را داشت. (اطمینان: بالا.)
- شناسه‌ها `IDENTITY` نیستند و از `FMK.IDGeneration` و `FMK.spGetNextId` می‌آیند. برای خواندن مشکلی نیست، ولی برای نوشتن در سپیدار (حالت همراه) مهم است. (اطمینان: متوسط تا بالا.)

**ساختار حساب**
- سطوح رسمی: **گروه، کل، معین**، به‌اضافهٔ **تفصیلی شناور** (DL، Detail Level) و تفصیلی ۱ و ۲. اشخاص، بانک‌ها، صندوق‌ها و مراکز هزینه با `DLRef` به `ACC.DL` وصل می‌شوند. (اطمینان: بالا. صفحه‌های رسمی سپیدار به نقل از ADR سبلان، و کد یکپارچه‌سازهای شخص ثالث.)
- `ACC.Account`: ستون‌های `AccountId`، `Code`، `Title`، `Type` (سطح)، `ParentAccountRef`، `BalanceType` (ماهیت)، `HasDL`، `HasCurrency`، `HasTracking`، `OpeningBalance`، `CashFlowCategory`، `IsActive`.
- `ACC.Voucher` و `ACC.VoucherItem`: ستون‌های `VoucherRef`، `RowNumber`، **`AccountSLRef`** (حساب معین)، **`DLRef`** (تفصیلی)، `Debit`، `Credit`، `CurrencyRef`، `CurrencyRate`، `CurrencyDebit`، `CurrencyCredit`، `TrackingNumber`، `TrackingDate`، `IssuerEntityName`/`IssuerEntityRef` (سند منشأ)، `Description`. جدول‌های `ACC.OpeningOperation(Item)` و `ACC.GLVoucher(Item)` هم وجود دارند.
- *یادداشت اخلاقی:* فهرست ستون‌ها در یک کپی غیررسمی از اسکریپت‌های نصب سپیدار در GitHub دیده شد که شامل فایل پشتیبان یک مشتری واقعی هم بود. **به آن لینک نمی‌دهیم و از کدش استفاده نمی‌کنیم.** همین ستون‌ها در کد یکپارچه‌سازهای شخص ثالث (Hesabyar-Backend) و در طرح حسابیکس هم آمده‌اند. **نکته‌های پنهان** (از گزارش انتقال واقعی حسابیکس؛ اطمینان: بالا)
1. `NetPrice` در فاکتور **اضافات را شامل می‌شود.** دوباره جمع کردن اضافات در یک مورد ۲۰٬۰۰۰ ریال خطا ساخت.
2. سپیدار ماندهٔ انبار را در افتتاحیهٔ سال بعد **تکرار می‌کند.** اگر موجودی تجمعی بین سال‌ها محاسبه شود، یک «پل» برای حذف این تکرار لازم است.
3. بین خلاصهٔ رسمی `ItemStockSummary` و جمع گردش‌ها اختلاف دیده شد (۷۳ قلم). اختلاف باید در سند جدا و قابل ردیابی بیاید و سند مبدأ اصلاح نشود.
4. ۵٬۴۳۸ ردیف انبار قیمت مبدأ داشتند و **۶٬۱۲۶ ردیف قیمت قطعی نداشتند.** ارزش این ردیف‌ها «نامشخص» است، نه صفر. سود فاکتورهای واردشده را تا وقتی بها کامل نیست حساب نکنید.
5. تخصیص دریافت به فاکتور **فقط** از `PartyAccountSettlementItem` می‌آید و نباید خودکار پخش شود. `IsSettled=false` لزوماً به معنی بی‌اعتباری نیست (منطق `SLS.fnInvoiceRemaining`).
6. ADR سبلان: پشتیبانِ در دسترس، جزئیات اسناد ۱۴۰۴ را برای چند ماه نداشت. **کامل بودن سال مالی را باید آزمود و فرض نکرد.**

**پشتیبان**
- پشتیبان **`.bak` بومی SQL Server** است: «ساختار فشرده و باینری پایگاه دادهٔ SQL Server». با بازیابی سپیدار یا SSMS خوانده می‌شود و SabalanERP آن را با `RESTORE VERIFYONLY` بررسی کرده است. مسیر پیش‌فرض `C:\Sepidar\Backup` یا پوشهٔ پشتیبان SQL است. در شبکه، پشتیبان روی دیسک سرور ذخیره می‌شود. **رمز** اختیاری است و در بخش فشرده‌سازی تنظیم می‌شود. پشتیبان خودکار روزانه یا دوره‌ای با سقف تعداد نسخه است. بازیابی فقط روی نسخهٔ هم‌سطح یا جدیدتر سپیدار و SQL ممکن است. (اطمینان: متوسط تا بالا.)
- **رمز روی پشتیبان SQL** (`PASSWORD`/`MEDIAPASSWORD`) طبق مستندات Microsoft «حفاظت ضعیفی» است و فایل را رمزنگاری نمی‌کند. با این حال **ما آن را دور نمی‌زنیم** و رمز را از مالک می‌گیریم (بخش ۶).
- [اصلاح‌شده در راستی‌آزمایی] طبق مستند `BACKUP` مایکروسافت، **از SQL Server 2012 به بعد گزینه‌های `PASSWORD` و `MEDIAPASSWORD` برای ساختن پشتیبان حذف شده‌اند.** فقط بازیابی پشتیبان‌های رمزدارِ قدیمی هنوز ممکن است. پس روی SQL 2012 به بعد، «رمز روی پشتیبان» سپیدار به احتمال زیاد در لایهٔ خود نرم‌افزار ساخته می‌شود (مثلاً بسته‌بندی یا فشرده‌سازی رمزدار). در آن صورت فایل یک `.bak` خام نیست که مستقیم `RESTORE` شود.
  - مقالهٔ ferdowsi.cloud هم پسوند `.bak` را نام نمی‌برد و فقط می‌گوید خروجی «ساختار فشرده و باینری» دارد.
  - **اقدام:** آپلودگر B2 باید پیش از `RESTORE` امضای فایل را بسنجد: هدر MTF/`TAPE` برای پشتیبان بومی SQL، و `PK` برای ZIP. اگر قالب ناشناخته بود، از مشتری بخواهیم پشتیبان **بدون رمز** بگیرد، یا مسیر B1 یا اکسل را برویم. (اطمینان: متوسط.)

**ورود و خروج اکسل**
- «ارسال به اکسل» از فرم‌های اطلاعات پایه (کالا، طرف حساب) و گزارش‌ها.
- **«ارسال و دریافت اطلاعات» (کانورت)** با الگوهای خالی برای طرف حساب، کالا و خدمت، **سند حسابداری** (از پایین فهرست اسناد: «الگوی دریافت سند حسابداری») و دریافت. فایل باید **Excel 97-2003 (`.xls`)** باشد. تغییر ستون‌های الگو دریافت را خراب می‌کند. اسناد فقط وقتی وارد می‌شوند که درخت حساب و تفصیلی‌ها از قبل در مقصد باشند. (اطمینان: متوسط.)

**API**
- **وب‌سرویس سپیدار:** مستندات رسمی v110 در `sepidarsystem.com/api/sepidar/` است و یک آینهٔ غیررسمی Swagger برای v112 هم وجود دارد. سرور محلی `http://localhost:7373/api` است. ثبت دستگاه (`/Devices/Register`) با RSA و `IntegrationID` انجام می‌شود و بعد `/Users/Login` با JWT. ۲۰۸ مسیر دارد: Customers، Items، Items/Inventories، Invoices، ReturnedInvoices، Quotations، Orders، Receipts، BankAccounts، Banks، Currencies، Units، Stocks، PriceNoteItems، SaleTypes، Distribution و … **هیچ endpoint برای حساب، سند یا چک ندارد.** (اطمینان: بالا، شمارش مستقیم روی فایل Swagger.)
  - [راستی‌آزمایی: تأیید و تکمیل] شمارش دوباره روی `sepidar-api.json` نتیجه را تأیید کرد: ۲۰۸ مسیر، ۲۳۰ عملیات و `servers: http://localhost:7373/api`. فیلد `info.version` مقدار 112 دارد، هرچند README مخزن از «نسخه 111» حرف می‌زند.
  - **`/Receipts` فقط `POST` (ثبت) دارد و GET ندارد.** پس دریافت‌ها از وب‌سرویس **خواندنی نیستند** و برای مهاجرت باید از SQL (`RPA.*`) خوانده شوند.
  - موارد خواندنی: Customers، Items و Items/Inventories، Invoices (BasedOnDate و …)، ReturnedInvoices، BankAccounts، Currencies، Stocks و Units.
  - گروه `Reports` (`PrintReport`/`PrintReportWithParameter`) هم وجود دارد. اینکه بتوان از آن تراز آزمایشی گرفت بررسی نشد.
  - چند مسیر نسخه‌های متفاوت دارند (`#101`، `#104`، `#109` بسته به هدر `GenerationVersion`). کلاینت باید نسخه‌محور باشد.

**سپیدار ابری**
- محصول ابری رسمی و جدا از نسخهٔ نصبی (`sepidarsystem.com/products/sepidar-cloud/`). اطلاعات پایه با قالب‌های استاندارد اکسل وارد می‌شود. مسیر رسمی انتقال از نصبی به ابری در منابع پیدا نشد. (اطمینان: متوسط.)

**ابزار و خدمات تبدیل موجود**
- **حسابیکس، «ورود لایو سپیدار»:**
  1. اتصال فقط‌خواندنی به SQL و کشف ساختار از `INFORMATION_SCHEMA`.
  2. snapshot خام هر رکورد با کلید پایدار، payload JSON و hash.
  3. همگام‌سازی idempotent با polling.
  4. نگاشت بومی به این ترتیب: ارز و سال، انبار، اشخاص، کالا، درخت حساب، اسناد، فاکتورها، انبار و تسویه‌ها.
  5. کل تبدیل در یک تراکنش.
  6. پذیرش: ۴٬۵۵۹ سند و ۱۳٬۸۷۹ سطر دفتر؛ جمع هر سمت ۱٬۳۷۰٬۶۱۳٬۵۲۰٬۱۱۱ ریال و برابر با مبدأ؛ ۵۶ تست موفق.
- **SabalanERP:** فایل `.bak` را به‌صورت snapshot تغییرناپذیر و هش‌شده می‌گیرد، delta بین دو snapshot را مقایسه می‌کند و یک دورهٔ اجرای موازی دارد که در آن سپیدار مرجع قانونی می‌ماند. ADR-0067 می‌گوید فقط تراز افتتاحیه و اقلام باز منتقل شود و تاریخچه به آرشیو برود.
- شرکت‌های خدمات کانورت با اکسل، مثل نمایندگی‌های سپیدار.

### ۳.۴ حسابفا (Hesabfa؛ ابری)

- **دسترسی به دیتابیس:** طبق پرسش‌های متداول حسابفا، «خروجی گرفتن مستقیم فایل پایگاه داده به دلایل امنیتی ممکن نیست». پشتیبان‌ها روی فضای ابری حسابفا نگهداری می‌شوند (تا ۱۰ نسخهٔ دستی به‌اضافهٔ پشتیبان شبانه). فایل پشتیبان از «لیست کسب‌وکارها» قابل دانلود است، اما فقط برای بازگردانی داخل حسابفا. اطلاعات کسب‌وکار را هم می‌توان **به اکسل** دانلود کرد. (اطمینان: متوسط تا بالا.)
- **ورود اکسل در حسابفا:** فقط اشخاص و کالا/خدمات، با ماندهٔ بدهکار یا بستانکار و موجودی اول دوره که به تراز افتتاحیه می‌رود. (اطمینان: بالا.)
- **API رسمی** (مستندات `hesabfa.com/help/api/*` و Postman Collection عمومی):
  - همهٔ درخواست‌ها `POST` با بدنهٔ JSON به `https://api.hesabfa.com/v1/{module}/{method}` هستند.
  - احراز هویت: `apiKey` به‌اضافهٔ `loginToken` (توکن کسب‌وکار، از «تنظیمات ← API») یا `userId`/`password`. برخی متدها `yearId` می‌گیرند.
  - ماژول‌ها و متدها:
    - `contact` (get، getById، getcontacts، save، batchsave، delete، findByPhoneOrEmail)
    - `item` (get، getitems، getByBarcode، save، batchsave، GetQuantity، UpdateOpeningQuantity)
    - `invoice` (get، getinvoices، save، savepayment، SaveWarehouseReceipt، …)
    - `receipt` (get، getReceipts، save، save2)
    - **`document`** (get، **getdocuments**، save؛ آرتیکل‌ها با **`AccountPath`** مثل «بدهی‌ها : بدهی‌های جاری : پیش‌دریافت‌ها : …»)
    - `setting` (**GetAccounts**، **GetFiscalYears**، GetBanks، GetCashes، GetPettyCashes، GetCurrency، GetWarehouses، GetProjects، GetSalesmen، GetBusinessInfo، **GetChanges**، Get/SetChangeHook)
    - `report` (**trialbalance**، trialbalanceitems، journal، balancesheet، profitandlossstatement، debtorscreditors، inventory، bank، cash، pettyCash)
    - `warehouse`، `banktransfer`، `discountitem` و `inquiry`
  - صفحه‌بندی با `queryInfo` (`SortBy`، `SortAsce`، `Take`، `Skip`، `filters`).
  - [راستی‌آزمایی: تأیید] همهٔ مسیرهای بالا (از جمله `document/getdocuments`، `setting/GetAccounts`، `setting/GetChanges` و `report/trialbalance`) در Postman Collection به‌صورت `POST https://api.hesabfa.com/v1/...` آمده‌اند. افزونهٔ رسمی ووکامرس حسابفا (کد در مخزن SVN وردپرس) هم همین بدنه را می‌فرستد: `apiKey` و `userId` و `password` و `loginToken` با `Content-Type: application/json`.
    - همان افزونه آدرس جایگزین `http://api.hesabfa.ir/v1/` را هم دارد که برای سرورهای داخل ایران مفید است.
    - پاسخ یک پاکت `{Success, ErrorCode, ErrorMessage, Result}` است. کدهای خطا در افزونه: 100 InternalServerError، **101 TooManyRequests**، 104 MissingParameter، 105 ApiDisabled، 106 UserIsNotOwner، 107 BusinessNotFound، 108 BusinessExpired، 112 ObjectNotFound، 113 MissingApiKey، 114 ParameterIsOutOfRange و 190 ApplicationError.
  - نتیجه: **انتقال کامل حسابفا با API ممکن است.** حساب‌ها، اشخاص، کالا، اسناد و فاکتورها خوانده می‌شوند و با `report/trialbalance` تطبیق می‌شوند. (اطمینان: بالا.)
- **محدودیت نرخ:** در مستندات رسمی دیده نشد. یک ابزار شخص ثالث «۱۲۰ درخواست در دقیقه» را رعایت می‌کند. (اطمینان: پایین.) کلاینت ما باید backoff، retry و کنترل سرعت داشته باشد.
  - [راستی‌آزمایی: نامطمئن، با شواهد متناقض] وجود محدودیت قطعی است (کد خطای `101 TooManyRequests`). ولی مقدار آن مشخص نیست:
    - افزونهٔ رسمی حسابفا بعد از هر درخواست `sleep(1)` می‌کند، با توضیح «Maximum request per minutes is 60 times».
    - ابزار شخص ثالث ۱۲۰ در دقیقه و صبر دست‌کم ۱۰ ثانیه پس از خطای 101 را می‌گوید.
  - **پیش‌فرض محافظه‌کارانهٔ ما:** حداکثر ۱ درخواست در ثانیه برای هر کسب‌وکار، و با `ErrorCode=101` دست‌کم ۱۰ ثانیه صبر و backoff نمایی. مقدار قابل تنظیم باشد، نه hardcode.

### ۳.۵ پارمیس (Parmis؛ parmisit.com)

- **نسل‌ها:** پارمیس پرو (توسعه متوقف شده و فقط پشتیبانی می‌شود) و **پارمیس استار** (ERP یکپارچه با پرتال تحت وب). (اطمینان: متوسط.)
- **موتور:** SQL Server. مقالهٔ آموزشی پارمیس می‌گوید فایل‌های اطلاعاتی با پسوند `mdf` و `ldf` در پوشهٔ `Data` مسیر نصب نگهداری می‌شوند. (اطمینان: متوسط تا بالا.)
- **ورود اکسل:** «بیشتر اطلاعات اولیه را می‌توان با اکسل به پارمیس استار منتقل کرد». ورود کالا، چک‌های دریافتی و پرداختی و کارکرد پرسنل از اکسل بسته به نسخه است. گزارش‌ها خروجی اکسل دارند. (اطمینان: متوسط.)
- **API:** افزونهٔ ووکامرس و «API اختصاصی» برای فروشگاه‌های دیگر که از پشتیبانی پارمیس گرفته می‌شود. مستندات عمومی پیدا نشد. (اطمینان: متوسط.)
- **اسکیما:** عمومی نیست. برای پیاده‌سازی باید probe روی دیتابیس واقعی اجرا شود.

## ۵. پیشنهادهای طراحی برای حساب‌کتاب

### ۵.۱ اصول غیرقابل مذاکره (قرارداد صحت انتقال)

1. **فقط‌خواندنی روی مبدأ.** هیچ `INSERT`، `UPDATE` یا `DELETE` روی سیستم قبلی انجام نمی‌شود. اتصال SQL با `ApplicationIntent=ReadOnly` و کاربری با کمترین دسترسی است.
   - [اصلاح‌شده در راستی‌آزمایی] `ApplicationIntent=ReadOnly` فقط **اعلام نیت و مسیریابی** برای Always On Availability Group است. طبق مستند مایکروسافت، اگر مقصد ویژه‌ای (replica خواندنی) نباشد، اتصال به همان دیتابیس عادی می‌رود. **روی سرور مستقل هلو یا سپیدار جلوی نوشتن را نمی‌گیرد.** فقط‌خواندنی بودن باید این‌طور تضمین شود:
     - (الف) login/کاربر اختصاصی که فقط عضو `db_datareader` است، بدون `db_owner` یا `sysadmin`، با `DENY INSERT, UPDATE, DELETE, EXECUTE` در صورت امکان. اگر مشتری فقط `sa` داد، عامل باید هشدار دهد.
     - (ب) کد عامل فقط `SELECT` بفرستد، با allowlist کوئری‌ها و تست.
     - (ج) در صورت امکان، خواندن از **کپی بازیابی‌شده** (B2) به‌جای دیتابیس زنده.
2. **رد کردن بهتر از حدس زدن.** خطی که نگاشت قطعی ندارد کل سند را `Blocked` می‌کند. نسبت دادن به «اولین بانک»، حساب معلق یا تطابق تقریبی نام ممنوع است.
3. **هر سند مبدأ حداکثر یک‌بار ثبت می‌شود.** پارتیشن انحصاری داریم و کلید منبع یکتا است: `(source_system, source_db, source_table, source_key)`.
4. **سند نامتوازن منتقل نمی‌شود** (تلورانس ۰). بستن اختلاف با حساب «اختلاف تراز افتتاحیه» فقط برای افتتاحیه، فقط با گزارش صریح و فقط اگر اختلاف در خود مبدأ باشد مجاز است.
5. **idempotent و قابل ردیابی.** هر اجرا یک `import_run` دارد با hash بسته، نسخهٔ ابزار و نسخهٔ پروفایل نگاشت. اجرای دوباره رکورد تکراری نمی‌سازد.
6. **ثبت از مسیر سرویس‌های دامنه**، نه insert خام در جدول‌های دفتر، تا قواعد تراز، قفل دوره، شماره‌گذاری و ممیزی رعایت شوند.
7. **پذیرش = تطبیق.** کار تمام نیست تا گزارش تطبیق «اختلاف توضیح‌داده‌نشده = ۰» نشان دهد.

### ۵.۲ معماری: سه کانال ورودی و یک قالب میانی

```
 ┌──────────────── منابع ────────────────┐
 │ A) API ابری: حسابفا، وب‌سرویس سپیدار (اطلاعات پایه)، TncHoloo، Sync محک
 │ B) SQL Server: هلو، سپیدار، محک، پارمیس
 │    B1) «عامل انتقال» ویندوزی روی شبکهٔ مشتری (فقط‌خواندنی)
 │    B2) آپلود .bak → بازیابی در sandbox ایزوله → استخراج → نابودی
 │ C) قالب‌های جهانی Excel/CSV (هر نرم‌افزار دیگر + خروجی اکسل همین‌ها)
 └───────────────────────┬───────────────┘
                         ▼
        بستهٔ تبادل حساب‌کتاب (HIF) — zip امضاشده
        manifest.json + entities/*.jsonl + raw/*.jsonl
                         ▼
 Staging (PostgreSQL، schema جدا برای هر import_run، RLS مستاجر)
   → Normalize → Map → Validate → Preview → Commit → Reconcile → (Rollback)
```

- **چرا قالب میانی (HIF)؟** آداپتور هر فروشنده فقط «HIF تولید می‌کند» و موتور واردکننده یکی است. نسخهٔ نصب محلی و SaaS از یک کد استفاده می‌کنند. بسته را می‌توان آفلاین منتقل کرد، مثلاً عامل روی شبکهٔ مشتری اجرا شود و فقط بستهٔ رمزنگاری‌شده آپلود شود. تست‌ها هم با بسته‌های مصنوعی ساده می‌شوند.
- **ساختار پیشنهادی HIF v1:**
  - `manifest.json`: `source_system`، `source_version`، `fingerprint` (فهرست جدول‌ها و ستون‌ها)، `extracted_at`، `extractor_version`، `currency_unit`، `date_mode`، `fiscal_years[]`، شمار ردیف هر جدول، `sha256` هر فایل و امضا.
  - `entities/`: `fiscal_years`، `currencies`، `accounts` (درخت، سطح، ماهیت، `legacy_code`)، `detail_accounts` (تفصیلی‌ها)، `parties`، `items`، `units`، `item_groups`، `warehouses`، `bank_accounts`، `cash_boxes`، `opening_balances`، `vouchers` و `voucher_lines`، `invoices` و `invoice_lines`، `receipts_payments`، `cheques` (با وضعیت و صیادی)، `stock_movements`، `tax_mappings`
  - `raw/`: snapshot خام هر جدول مبدأ (payload، `source_key`، `content_hash`) برای ممیزی و نگاشت‌های بعدی
- **B2 (بازیابی `.bak` در SaaS):**
  - کانتینر SQL Server روی Linux با `MSSQL_PID=Express`، بدون شبکهٔ خروجی و تک‌مصرف.
  - مراحل: `RESTORE HEADERONLY` (نسخه، collation، نام دیتابیس)، `RESTORE FILELISTONLY`، `RESTORE VERIFYONLY`، سپس `RESTORE ... WITH MOVE`، استخراج و حذف کانتینر و فایل.
  - محدودیت‌ها: Express برای هر دیتابیس سقف **۱۰ GB** دارد (SQL 2022). پشتیبانِ ساخته‌شده روی SQL 2008 به بعد روی 2022 بازیابی می‌شود، ولی **پشتیبان نسخهٔ جدیدتر روی نسخهٔ قدیمی‌تر بازیابی نمی‌شود.** پس sandbox باید جدیدترین نسخهٔ SQL را داشته باشد.
  - [اصلاح‌شده در راستی‌آزمایی] جدیدترین نسخه **SQL Server 2025 (17.x)** است، با image `mcr.microsoft.com/mssql/server:2025-latest`.
    - طبق جدول Scale limits، **سقف دیتابیس در Express 2025 برابر ۵۰ GB** است (در 2022 و قبل ۱۰ GB بود). سقف‌های دیگر: کمترِ ۱ سوکت یا ۴ هسته، و حافظهٔ buffer pool برابر ۱٬۴۱۰ MB.
    - مستند ارتقای 2025 تأیید می‌کند پشتیبان SQL 2008 به بعد روی 2025 بازیابی می‌شود. سطح سازگاری 100 هم حفظ می‌شود، و سطح 90 (2005) به 100 ارتقا می‌یابد.
    - مقادیر `MSSQL_PID` در 2025: `Express`، `Standard`، `EnterpriseCore`، `EnterpriseDeveloper`، `StandardDeveloper` و `Evaluation`. مقدار `Web` حذف شده است.
    - **پیشنهاد:** sandbox روی 2025 Express. (پیش از تولید، شرایط مجوز Express برای استفادهٔ میزبانی‌شده در SaaS و در دسترس بودن MCR از دیتاسنتر مقصد بررسی شود.)
  - برای دیتابیس بزرگ‌تر از **۵۰ GB** (روی 2025) باید مجوز Standard تهیه شود یا عامل B1 روی سرور مشتری اجرا شود. مجوز Developer (در 2025: Enterprise/Standard Developer) برای محیط تولید مجاز نیست.
  - به‌خاطر نکتهٔ بخش ۳.۲ دربارهٔ رمز پشتیبان، پیش از `RESTORE` امضای فایل بررسی شود (MTF یا ZIP یا ناشناخته).
- **B1 (عامل ویندوزی):** یک فایل اجرایی کوچک و امضاشده، بدون نصب. instance و دیتابیس‌ها را کشف می‌کند، probe را اجرا می‌کند، HIF رمزنگاری‌شده تولید می‌کند و آن را آپلود یا ذخیره می‌کند. رمز SQL را خود کاربر وارد می‌کند و هیچ‌جا ذخیره نمی‌شود. دو گزینه برای پیاده‌سازی: Python با PyInstaller یا .NET. *(سؤال باز: پذیرش امضای کد و آنتی‌ویروس‌ها.)*
- **کتابخانه‌ها (Python):**
  - SQL Server: `pyodbc` با ODBC Driver 18 (TLS پیش‌فرض) یا `pymssql`
    - [راستی‌آزمایی: تأیید با قید] در ODBC Driver 18 پیش‌فرض `Encrypt=yes` است و گواهی سرور بررسی می‌شود. نصب‌های هلو و سپیدار معمولاً گواهی خودامضا دارند، پس اتصال بدون `TrustServerCertificate=yes` شکست می‌خورد.
    - این تنظیم فقط برای شبکهٔ محلی مشتری و با هشدار مجاز است. در SaaS هرگز به سرور راه دور با این گزینه وصل نشویم.
    - جدول سازگاری فعلی Driver 18 فقط **SQL Server 2017 به بعد** را «تست‌شده» می‌داند. سیستم‌عامل‌های پشتیبانی‌شده‌اش هم Windows Server 2016 به بعد و Windows 11 هستند.
    - پس عامل B1 روی سرورهای قدیمی مشتری (SQL 2008 R2، Windows 7 یا Server 2008/2012) باید fallback داشته باشد: Driver 17، `pymssql`/FreeTDS، یا درایوری که خود نصب SQL دارد. این ترکیب روی ماشین مجازی قدیمی آزموده شود.
    - SQL 2008 R2 بدون وصله‌های TLS 1.2 ممکن است با کلاینت‌های جدید دست ندهد. (اطمینان: متوسط.)
  - اکسل: `openpyxl` برای `.xlsx` و `xlrd` برای `.xls` (الگوهای 97-2003 سپیدار و هلو)
  - CSV: تشخیص کدگذاری cp1256، UTF-8 و UTF-16LE
  - تاریخ جلالی: `jdatetime`

### ۵.۳ دامنهٔ انتقال: چه چیزی منتقل شود؟

| سطح | محتوا | کاربرد | پیش‌فرض؟ |
|---|---|---|---|
| **۰، پایه + افتتاحیه** (توصیه) | سال مالی، ارز، درخت حساب، تفصیلی‌ها، اشخاص، کالا و واحد و گروه، انبار، بانک، صندوق، تنخواه؛ **تراز افتتاحیه** در تاریخ cutover؛ **اقلام باز**: ماندهٔ هر شخص (و در صورت امکان فاکتورهای باز)، **چک‌های باز** با وضعیت، **موجودی مقداری و ریالی هر کالا در هر انبار**، ماندهٔ هر بانک، صندوق و تنخواه | بیشتر مشتریان کوچک (کافه، کفش‌فروشی، لوازم برقی) | ✅ |
| **۱، سال جاری کامل** | سطح ۰ در ابتدای سال، به‌اضافهٔ همهٔ اسناد، فاکتورها، دریافت‌ها و حواله‌های سال جاری تا cutover | cutover میانهٔ سال؛ نیاز به گزارش سالانهٔ کامل و اظهارنامه | اختیاری |
| **۲، تاریخچهٔ آرشیوی** | سال‌های قبل به‌صورت **آرشیو فقط‌خواندنی و قابل جستجو** (raw و گزارش‌ها)، بدون ثبت در دفتر فعال | مراجعهٔ حسابرسی و مالیاتی | ✅ (ارزان، چون raw داریم) |
| **۳، تاریخچهٔ کامل ثبت‌شده** | ثبت اسناد سال‌های قبل در دفترهای جدا و قفل‌شده با lineage | درخواست خاص یا حسابرسی | فقط سفارشی |

- **توصیهٔ پیش‌فرض:** cutover در **ابتدای سال مالی** (اول فروردین ۱۴۰۶) یا ابتدای ماه، و انتقال سطح ۰ به‌اضافهٔ آرشیو سطح ۲. این همان تصمیم ADR-0067 SabalanERP است: «تراز افتتاحیهٔ تطبیق‌شده و اقلام باز، نه بازسازی تمام تاریخچه». بازسازی تاریخچه یک «دفتر دوم» می‌سازد که ممکن است با مبدأ فرق داشته باشد.
- **حالت همراه (Companion)، اختیاری برای مشتری محتاط:** یک دورهٔ ۱ تا ۲ ماهه اجرای موازی. سیستم قبلی دفتر رسمی می‌ماند و حساب‌کتاب snapshotهای دوره‌ای را می‌خواند و تطبیق می‌دهد. سپس «انتقال مرجعیت» یک‌باره انجام می‌شود. (الگو از SabalanERP و طرح biza-miz.)

### ۵.۴ خط لولهٔ مرحله‌ای (state machine)

```
draft → probed → extracted → normalized → mapped → validated → previewed
      → committing → committed → reconciled ✅   |  → rolled_back
```

| مرحله | کار | خروجی و کنترل |
|---|---|---|
| **۱. Discover / Probe** | تشخیص محصول با امضای جدول‌ها، نسخه و collation، شمار ردیف‌ها، سال‌های مالی، حالت ارز، واحد پول و نوع تاریخ | گزارش probe؛ انتخاب دیتابیس و سال؛ مقایسه با «پروفایل‌های شناخته‌شده». ناشناخته بودن به معنی fallback به اکسل یا پروفایل دستی است |
| **۲. Extract** | snapshot خام و تغییرناپذیر | HIF با hash و شمار ردیف. برابری شمار ردیف با probe الزامی است |
| **۳. Normalize** | حروف، ارقام، تاریخ، مبلغ، trim، کدها | گزارش تغییرات نرمال‌سازی؛ متن اصلی در raw می‌ماند |
| **۴. Map** | نگاشت حساب‌ها (بخش ۵.۵)، اشخاص، کالا، انبار، بانک و صندوق | **پروفایل نگاشت** نسخه‌دار با قفل. «حافظهٔ نگاشت» برای هر نرم‌افزار مبدأ تا نگاشت‌های تأییدشدهٔ مشتریان قبلی پیشنهاد شوند |
| **۵. Validate** | قواعد Blocker و Warning | فهرست مشکلات با کد، شدت و ارجاع به رکورد مبدأ |
| **۶. Preview** | بدون نوشتن: تعداد و جمع هر موجودیت، **تراز آزمایشی پیش‌نمایش** کنار تراز مبدأ، نمونهٔ اسناد | تأیید انسانی (حسابدار مشتری یا تیم انتقال). دکمهٔ Commit تا صفر شدن Blockerها غیرفعال است |
| **۷. Commit** | ثبت از سرویس‌های دامنه، دسته‌ای و تراکنشی؛ `import_run_id` روی هر رکورد؛ اسناد واردشده برچسب «واردشده» دارند و ویرایششان محدود است | checkpoint و resume؛ idempotent |
| **۸. Reconcile** | تطبیق مبدأ و مقصد (بخش ۵.۷) | گزارش پذیرش PDF/اکسل برای امضای مشتری |
| **۹. Rollback** | حذف همهٔ رکوردهای `import_run_id`، فقط وقتی سند کاربری جدیدی به آن‌ها وابسته نشده باشد | لاگ ممیزی |

**قواعد اعتبارسنجی نمونه**
- Blocker:
  - سند نامتوازن
  - سطر با حساب بدون نگاشت
  - شخص، بانک یا صندوق حل‌نشده
  - کد تکراری در یک نوع موجودیت
  - تاریخ خارج از سال‌های مالی
  - ارجاع به رکورد ناموجود
  - مبلغ منفی در جایی که ممنوع است
  - مصرف یک `Sanad_Code` در دو ماژول
- Warning:
  - کد ملی یا اقتصادی نامعتبر
  - موجودی منفی
  - کالای بدون واحد یا گروه
  - قیمت یا بهای نامعلوم
  - حساب بدون گردش
  - شخص بدون نام
  - اختلاف قیمت `ARTICLE` و `ArticlePrice`

### ۵.۵ نگاشت کدینگ حساب (کل / معین / تفصیلی)

**مدل حساب‌کتاب (پیشنهاد)**
- درخت حساب با عمق آزاد و سطوح استاندارد **گروه، کل، معین**. هر حساب **نقش (role)**، **ماهیت** (بدهکار، بستانکار یا آزاد)، **نوع گزارش** (ترازنامه، سود و زیان یا انتظامی) و **`legacy_code` / `legacy_path`** دارد.
- **تفصیلی‌ها به‌صورت بُعد (dimension)** مدل شوند، نه حساب: شخص، بانک، صندوق، تنخواه، مرکز هزینه، پروژه و … . این همان «تفصیلی شناور» سپیدار است. چند سطح تفصیلی (۱ و ۲) روی یک آرتیکل مجاز است. هر حساب معین مشخص می‌کند کدام ابعاد را می‌پذیرد یا الزامی می‌کند (مثل `HasDL` در سپیدار).
- **نقش‌های استاندارد** (برای نگاشت خودکار):

| دسته | نقش‌ها |
|---|---|
| نقد و بانک | `CASH`، `PETTY_CASH`، `BANK` |
| دریافتنی‌ها | `AR_TRADE`، `NOTES_RECEIVABLE`، `CHEQUES_IN_COLLECTION` |
| پرداختنی‌ها | `AP_TRADE`، `NOTES_PAYABLE`، `LOANS`، `CUSTOMER_ADVANCES` |
| سایر دارایی‌ها | `INVENTORY`، `PREPAYMENTS`، `VAT_RECEIVABLE`، `FIXED_ASSET_*` |
| مالیات | `VAT_PAYABLE` |
| حقوق صاحبان سهام | `PARTNER_CURRENT`، `CAPITAL`، `RETAINED_EARNINGS`، `OPENING_BALANCE_DIFF` |
| فروش | `SALES`، `SALES_RETURNS`، `SALES_DISCOUNTS` |
| خرید و بها | `PURCHASES`، `PURCHASE_RETURNS`، `PURCHASE_DISCOUNTS`، `COGS` |
| درآمد و هزینه | `OTHER_INCOME`، `EXPENSE_*` |
| کنترلی و انتظامی | `MEMO_*` (انتظامی)، `CONTROL_SKIP` |

**ساختار مبدأها**
- **هلو:** کلید `Col(3) | Moien(4) | Tafzili`. کل‌ها کد ثابت دارند (فهرست ۳.۱). اشخاص از طریق `CustomerSarfasl` و بانک‌ها از طریق `ACOUND_N` به تفصیلی وصل‌اند.
- **سپیدار:** `ACC.Account` (گروه، کل، معین با `ParentAccountRef`) به‌اضافهٔ `ACC.DL` شناور. آرتیکل `AccountSLRef + DLRef` دارد.
- **حسابفا:** مسیر متنی درخت (`AccountPath`، سطوح با « : » جدا می‌شوند). اشخاص، بانک‌ها و کالاها زیرحساب‌های سیستمی‌اند.
- **محک و پارمیس:** پس از probe مشخص می‌شود.

**الگوریتم نگاشت** (الهام از سه لایهٔ Holoo2Hesabix و ADR-0064 سبلان)
1. برای هر سرفصل یا آرتیکلِ دارای مبلغ، کلید را از **دقیق‌ترین سطح** حل کن: اول تفصیلی، بعد معین، بعد کل.
2. **لایهٔ A، زیردفتر:** اگر نقش مبدأ صندوق، بانک یا شخص است، به موجودیت حساب‌کتاب (بُعد) و حساب نقش‌دار نگاشت کن. جهت AR یا AP را از ماهیت خالص مانده تعیین کن، نه فقط از کد.
3. **لایهٔ B، حساب استاندارد:** اگر ماهیت با یکی از حساب‌های seed یکی است، به همان نگاشت کن (مثلاً `901` هلو به `SALES`).
4. **لایهٔ C، حساب اختصاصی:** اگر معادل نیست یا مشتری می‌خواهد معین جدا بماند، حساب اختصاصی زیر **والدِ هم‌ماهیت** بساز تا در سود و زیان درست طبقه‌بندی شود. فقط با تأیید کاربر در پیش‌نمایش.
5. **ممنوع:** نگاشت بر اساس `Contains` روی نام بدون تأیید، حساب پیش‌فرض برای «هزینهٔ ناشناس»، و انتخاب «اولین بانک».
6. **دو حالت محصول:**
   - «نگاشت به کدینگ استاندارد حساب‌کتاب» (پیش‌فرض؛ گزارش‌های آماده، مؤدیان و صورت‌های مالی درست کار می‌کنند)
   - «حفظ کدینگ قبلی من» (درخت مبدأ عیناً ساخته می‌شود و هر گره فقط یک **نقش** می‌گیرد). در هر دو حالت `legacy_code` نگه داشته و در جستجو و گزارش قابل نمایش است.
7. **قالب‌های آمادهٔ نگاشت برای هر فروشنده** (مثل جدول کل‌های ثابت هلو) نسخه‌دار در مخزن نگه داشته شوند. «حافظهٔ نگاشت» مستاجران (بی‌نام‌شده) را پیشنهاد دهد.
8. **کنترل ماهیت پس از نگاشت:** جمع گروه فروش مبدأ (`901 − 902 − 903 ± 904` در هلو) باید با گردش `SALES*` مقصد برابر باشد. همین برای خرید، بها، اشخاص و بانک‌ها.

### ۵.۶ جلوگیری از ثبت دوبل: پارتیشن انحصاری اسناد

ترتیب ارزیابی برای هر سند مبدأ (نمونهٔ هلو؛ برای سپیدار `IssuerEntityName/Ref` معادل است):

1. سند افتتاحیه → `OPENING`
2. فقط ردیف‌های کنترلی (`005`/`006`) یا بدون مبلغ → `SKIP_CONTROL`
3. سند چک (`Sanad_Type=5` یا ارجاع از `[Check]`) → `CHEQUE` (اثر از ماژول چک)
4. سند متصل به فاکتور غیرحذف‌شده یا `SaveFromFacture=1` → `INVOICE` (اثر از فاکتور و حواله)
5. هزینه یا درآمد با طرف شخص، صندوق یا بانک → `EXPENSE_INCOME`
6. دریافت یا پرداخت (`Sanad_Type=20`) → `RECEIPT_PAYMENT`
7. بقیهٔ اسناد متوازن → `MANUAL`
8. باقی‌مانده → `UNCLASSIFIED`: باید صفر شود یا با دلیل در گزارش بیاید (Blocker)

- اگر حساب‌کتاب برای نوعی از سند ماژول تخصصی دارد (فاکتور، چک، دریافت/پرداخت)، سند از **همان ماژول** ساخته می‌شود تا GL و زیردفتر با هم شکل بگیرند. GL مشتق مبدأ دوباره پست نمی‌شود.
- در سطح ۰ (فقط افتتاحیه) این پارتیشن فقط برای **اعتبارسنجی** به کار می‌رود.

### ۵.۷ تطبیق و پذیرش

- **تراز آزمایشی:** گردش و مانده به تفکیک هر حساب مقصد در برابر مجموعه‌حساب‌های مبدأ نگاشت‌شده، برای هر سال و دوره. تلورانس صفر است. هر اختلاف یک «توضیح» با منبع دارد، مثل تفاوت سیستم دائمی موجودی.
- **زیردفترها:** ماندهٔ هر شخص (مثل `C_Code` هلو یا `PartyRef` سپیدار)، هر بانک و صندوق، و هر چک باز با مبلغ، سررسید و وضعیت.
- **انبار:** مقدار هر کالا در هر انبار برابر خلاصهٔ مبدأ. ارزش فقط برای ردیف‌های با بهای معلوم مقایسه شود و «ناقص» صریح علامت بخورد.
- **شمارش:** تعداد اسناد، فاکتورها، دریافت‌ها و چک‌های منتقل‌شده، به‌اضافهٔ ردشده‌ها با دلیل، برابر با تعداد مبدأ.
- **منبع تراز مبدأ:** برای SQL، کوئری مستقیم (مثل `holoo-trial-balance.ps1`). برای هلوی دارای وب‌سرویس، `Report/GetSarfasl` به‌عنوان کنترل مستقل دوم (با پارس `Decimal`). برای حسابفا، `report/trialbalance`. برای اکسل، از کاربر خواسته شود تراز آزمایشی مبدأ را هم آپلود کند.
- **خروجی:** گزارش پذیرش قابل امضا، و پرونده‌ای که در کسب‌وکار ذخیره می‌شود.

### ۵.۸ اجزای مدل داده در حساب‌کتاب

- `import_sources`: نوع منبع، تنظیمات اتصال رمزنگاری‌شده، بدون بازگرداندن رمز در API
- `import_runs`: وضعیت، دامنه، hash بسته، نسخهٔ ابزار و پروفایل، زمان‌ها، شمارنده‌ها
- `import_raw_records`: `run_id`، جدول مبدأ، `source_key`، `payload jsonb`، `content_hash`، tombstone. پارتیشن بر اساس مستاجر، با RLS
- `mapping_profiles` (نسخه‌دار و قفل‌شدنی) و `mapping_rules`
- `entity_mappings`: `(tenant, source_system, source_db, source_table, source_key) → (target_type, target_id, run_id)` با کلید یکتا
- `import_issues`: کد، شدت، پیام فارسی، ارجاع
- `reconciliation_reports`
- روی اسناد و موجودیت‌ها: `origin = 'import'`، `import_run_id`، `source_ref` (در `extra jsonb`)

### ۵.۹ امنیت فایل‌ها و داده

- فایل‌های آپلودی (`.bak`، `.zip`، اکسل) در فضای رمزنگاری‌شدهٔ همان مستاجر نگهداری و پس از N روز (مثلاً ۳۰، قابل تنظیم) **خودکار حذف** شوند. snapshot خام تا پایان پروژهٔ انتقال یا با انتخاب مشتری نگه داشته شود.
- دفاع در برابر فایل‌های خصمانه: zip-slip، zip bomb و تودرتو، XML bomb و XXE، فرمول CSV/اکسل (`=`، `+`، `-`، `@`) در خروجی‌ها، سقف اندازه و ردیف، و پارس در worker ایزوله.
- sandbox بازیابی `.bak` بدون شبکه و با منابع محدود اجرا شود و پس از کار نابود شود. لاگ‌ها بدون secret باشند.
- دادهٔ شخصی (کد ملی، موبایل، آدرس) با دسترسی کمینه. نقش «تیم انتقال» در پنل مدیریت پلتفرم دسترسی **محدود به زمان و با رضایت مستاجر** دارد و همهٔ کارهایش ممیزی می‌شود.

### ۵.۱۰ آزمون (برای رسیدن به خروجی مطمئن)

- **Fixtureهای مصنوعی برای هر فروشنده:** اسکیمای تقلیدی کوچک هلو و سپیدار با دادهٔ ساختگی (هرگز دادهٔ واقعی مشتری). تله‌های شناخته‌شده باید در آن‌ها باشند: فاکتور نوع 13 با `SaveFromFacture=0`، دو بانک هم‌نام، تخفیف فروش `903`، چک در جریان وصول، وام زیر `401`، `NetPrice` با اضافات، و تکرار افتتاحیهٔ انبار.
- **تست‌های golden:** تراز آزمایشی مقصد = مبدأ.
- **تست idempotency:** اجرای دوم هیچ درج یا ویرایشی ندارد و شناسه‌ها ثابت می‌مانند.
- **تست rollback** و **تست ناقص بودن** (قطع در میانه و resume).
- **تست ویژگی‌محور (property-based):** برای هر سند Σبدهکار = Σبستانکار و جمع زیردفتر = حساب کنترل.
- **تست فایل‌های خصمانه** و **تست حجم** (۱۰۰ هزار سند یا بیشتر، با سقف زمان).
- **تست سازگاری SQL:** کانتینر SQL Server 2022 با دیتابیس compatibility 100. [اصلاح‌شده در راستی‌آزمایی] هدف اصلی را **SQL Server 2025** بگذارید و 2022 را هم در ماتریس نگه دارید.
  - کوئری‌های استخراج نباید به `TRY_CONVERT` و توابع سطح 110 به بعد وابسته باشند، چون روی دیتابیس با compat 100 خطا می‌دهند (طبق مستند `TRY_CONVERT`).
  - روی کپی بازیابی‌شده در sandbox می‌توان سطح سازگاری را بالا برد. روی دیتابیس زندهٔ مشتری (B1) نه.
- پیش از عرضهٔ هر پروفایل جدید، دست‌کم **یک دیتابیس واقعی** با رضایت کتبی مالک و در محیط ایزوله آزموده شود.

### ۵.۱۱ اولویت پیاده‌سازی (پیشنهاد)

1. **MVP:** قالب‌های جهانی اکسل (حساب، شخص، کالا، تراز افتتاحیه، موجودی، چک‌های باز، و در صورت نیاز سند و فاکتور) با تطبیق ستون، حافظهٔ نگاشت، پیش‌نمایش و تطبیق. این مسیر برای **هر** نرم‌افزاری کار می‌کند.
2. **حسابفا با API:** کم‌ریسک‌ترین انتقال کامل.
3. **هلو با SQL** (عامل B1 و `.bak` B2): بیشترین سهم بازار اصناف و فروشگاه‌ها، که همان مشتریان اول ما هستند.
4. **سپیدار با SQL.**
5. **محک و پارمیس:** پس از دریافت دیتابیس نمونه با رضایت مالک و نوشتن پروفایل.
6. **حالت همراه** (اجرای موازی) برای مشتریان متوسط و بزرگ.

## ۶. قیود حقوقی و اخلاقی

1. **مالکیت داده:** داده‌های حسابداری متعلق به خود کسب‌وکار است. انتقال فقط با **درخواست و رضایت صریح و ثبت‌شدهٔ مالک یا نمایندهٔ قانونی** انجام می‌شود: پذیرش در ویزارد، و برای خدمت حضوری، فرم کتبی.
2. **دور زدن ممنوع:** رمز پشتیبان، رمز `sa`، قفل سخت‌افزاری یا نرم‌افزاری، لایسنس یا رمزنگاری فروشنده را **نمی‌شکنیم و برایش ابزار نمی‌سازیم.** اگر داده رمز دارد، رمز را مالک وارد می‌کند. اگر رمزنگاری فروشنده‌ای است، از **ابزار خروجی خود فروشنده** (اکسل یا API) یا از خود فروشنده درخواست می‌کنیم.
   - مبنا: ماده ۱ قانون جرایم رایانه‌ای (ماده ۷۲۹ قانون مجازات اسلامی، تعزیرات). دسترسی غیرمجاز به داده یا سامانهٔ «محفوظ به تدابیر امنیتی» جرم است و مجازات آن حبس ۹۱ روز تا یک سال یا جزای نقدی است. مبلغ جزای نقدی در متن‌های منتشرشده متفاوت است و پس از اصلاح ۱۴۰۳ بیشتر شده است. (اطمینان: بالا برای اصل حکم، پایین برای مبلغ.)
     - [اصلاح‌شده در راستی‌آزمایی] متن اصلی (۱۳۸۸) حبس ۹۱ روز تا یک سال **یا** جزای نقدی ۵ تا ۲۰ میلیون ریال **یا هر دو مجازات** است (ترجمهٔ ARTICLE 19: «and/or»). پس جمع دو مجازات هم ممکن است.
     - مبلغ تعدیل‌شدهٔ فعلی و ادعای «اصلاح ۱۴۰۳» از منبع اولیه تأیید نشد، چون سایت‌های حقوقی ایرانی در دسترس نبودند. پیش از درج در متن رضایت‌نامه، از مشاور حقوقی گرفته شود.
3. **حقوق نرم‌افزار فروشنده:** قانون حمایت از حقوق پدیدآورندگان نرم‌افزارهای رایانه‌ای (۱۳۷۹) تهیهٔ نسخهٔ پشتیبان را مجاز می‌داند و طبق یک منبع ثانویه (تبصرهٔ ماده ۷) تولید نرم‌افزار سازگار یا مکمل را هم با رعایت حقوق مادی پدیدآورنده مجاز می‌داند. (اطمینان: متوسط؛ شمارهٔ ماده و متن دقیق باید با متن رسمی تطبیق شود.)
   - **سیاست ما:** فقط **دادهٔ مشتری** را با اعتبارنامهٔ خود او می‌خوانیم.
   - کد، stored procedure، اسکریپت یا فایل‌های نصب فروشنده را کپی یا بازتوزیع نمی‌کنیم. کپی غیرمجاز اسکریپت‌های فروشنده در اینترنت را منبع کد نمی‌کنیم.
   - مستندات اسکیمای ما فقط شامل نام جدول و ستون لازم برای همکاری‌پذیری است.
   - شرایط استفادهٔ (EULA) هر فروشنده پیش از عرضهٔ تجاری پروفایل آن بررسی شود.
4. **نوشتن در سیستم فروشنده** (در حالت همراه) فقط از **API رسمی** انجام می‌شود. نوشتن مستقیم SQL در دیتابیس فروشنده ممکن است دفاتر قانونی مشتری را خراب کند و قرارداد پشتیبانی را باطل کند. پیشنهاد: در نسخهٔ اول **ممنوع** باشد.
5. **نگهداری دفاتر قدیم:** مشتری باید نسخهٔ پشتیبان سیستم قبلی و دفاتر قانونی را برای مراجعات مالیاتی نگه دارد. مادهٔ ۹۵ و ۱۸۱ قانون مالیات‌های مستقیم تکلیف نگهداری و ارائهٔ دفاتر را تعیین می‌کنند. **مدت دقیق نگهداری در این پژوهش تأیید نشد** (سؤال باز ۷). آرشیو سطح ۲ در حساب‌کتاب این نیاز را **جایگزین نمی‌کند**، فقط کمک می‌کند.
6. **حریم خصوصی:** کمینه‌سازی داده، رمزنگاری در حال انتقال و ذخیره، حذف زمان‌بندی‌شدهٔ فایل‌های آپلودی، ممیزی دسترسی تیم پشتیبانی، و قرارداد پردازش داده برای خدمت انتقال.

## ۷. سؤال‌های باز و روشن‌کننده (برای صاحب محصول)

1. **مشتریان اول** (کافه، کفش‌فروشی، لوازم برقی) الان با کدام نرم‌افزار و نسخه کار می‌کنند؟ می‌توانیم با رضایت کتبی یک **نسخهٔ پشتیبان واقعی** بگیریم تا پروفایل‌ها روی دادهٔ واقعی آزموده شوند؟
2. **سیاست cutover:** آیا پیش‌فرض «شروع از ابتدای سال یا ماه با تراز افتتاحیه و اقلام باز» قابل قبول است، یا مشتریان **تاریخچهٔ کامل** را در دفتر فعال می‌خواهند؟
3. **عامل ویندوزی:** آیا نصب یا اجرای یک فایل اجرایی کوچک روی سرور مشتری قابل قبول است؟ (نیاز به امضای کد و هماهنگی با آنتی‌ویروس.) یا فقط آپلود `.bak` و اکسل؟
4. **مجوز SQL Server در SaaS:** آیا Express (سقف ۱۰ GB در 2022؛ **۵۰ GB در 2025**، برای هر دیتابیس) کافی است، یا برای مشتریان بزرگ مجوز Standard یا اجرای عامل در سمت مشتری لازم است؟
5. **مدل کسب‌وکار انتقال:** سلف‌سرویس رایگان، یا «خدمت انتقال» پولی با تیم پشتیبانی برای مشتریان بزرگ؟ (روی نقش‌ها و دسترسی‌های پنل مدیریت پلتفرم اثر دارد.)
6. **کدینگ:** آیا اجازه می‌دهیم مشتری **کدینگ قبلی خودش** را نگه دارد، یا همه را به کدینگ استاندارد حساب‌کتاب می‌بریم و `legacy_code` را نگه می‌داریم؟
7. **حقوقی:** مدت قانونی نگهداری دفاتر و اسناد، متن رسمی مواد قانون نرم‌افزار، و متن رضایت‌نامهٔ انتقال باید با مشاور حقوقی بررسی شود.
8. **«حسابیار»** دقیقاً کدام محصول است؟ نرم‌افزارهای بخش ب را هم تأیید کنید: معین، راهکاران، همکاران سیستم، تدبیر، کسرا، دشت، آسان، حسیب، پیوند و ….
9. **حالت همراه:** آیا می‌خواهیم مشتری بتواند مدتی هلو یا سپیدار را کنار حساب‌کتاب نگه دارد؟ این حالت ارزش فروش دارد ولی پیچیدگی را بالا می‌برد.

**پیامدهای مستقیم برای پیاده‌سازی (خلاصه):**
1. sandbox بازیابی: **SQL Server 2025 Express** (سقف ۵۰ GB)، تشخیص امضای فایل پیش از `RESTORE`، و کوئری‌های سازگار با compat 100.
2. عامل B1: فقط‌خواندنی بودن با **مجوز کاربر SQL** تضمین شود، نه `ApplicationIntent`. ماتریس درایور برای ویندوز و SQL قدیمی تست شود.
3. کلاینت حسابفا: نرخ قابل تنظیم (پیش‌فرض ≤ ۱ درخواست در ثانیه)، مدیریت `ErrorCode=101` و دامنهٔ جایگزین `api.hesabfa.ir`.
4. پروفایل هلو: `Type IN (0,13,14)` + `SaveFromFacture`؛ TncHoloo `GetSarfasl` به‌عنوان کنترل تطبیق اختیاری.
5. پروفایل سپیدار: دریافت‌ها فقط از SQL (`RPA.*`) خوانده شوند.
6. هیچ کدی از مخزن حسابیکس (GPL-3.0) کپی نشود.
